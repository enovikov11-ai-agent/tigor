## GPU/VRAM Estimation (avoid trial-and-error deploys)

* **Current GPU: RTX PRO 6000 Blackwell 96GB GDDR7, 1.8 TB/s bandwidth.** Previous: RTX 3090 24GB (now in gaming PC).
* **CPU: 64-core @ 2.0 GHz** — high core count but low frequency. Shared across GPU inference, CPU inference (p-llama), compilation, etc. Prefer offloading all computation to GPU (CUDA graphs) to avoid CPU becoming the bottleneck.
* **VRAM budget = model weights + runtime overhead + KV cache.** All three compete for the same pool. Estimate all three before proposing a config.
* **Runtime overhead varies wildly by engine.** llama.cpp (C++): ~100s MB. vLLM/PyTorch: ~3-5 GiB (CUDA context, torch.compile, memory allocator). Measured: Qwen3.5-122B-A10B AWQ 4-bit loads at 73.2 GiB; with torch.compile + CUDA graphs, PyTorch uses 87.75 GiB total (~14.5 GiB overhead).
* **vLLM `--gpu-memory-utilization` caps total VRAM usage** (model + KV cache + overhead), not just KV cache. vLLM fills remaining space with KV cache up to this cap. At 0.99, speculative decoding (MTP rejection sampler) OOMs because all memory goes to KV cache with nothing left for sampler tensors (~970 MiB). Use 0.97 with MTP to leave headroom.
* **`--max-model-len` is a per-request cap, not a memory lever.** Lowering it does NOT reduce KV cache allocation — vLLM fills available memory regardless. It only limits how long a single request's context can be.
* **MTP (Multi-Token Prediction) is critical for single-request latency with `--enforce-eager`.** Without CUDA graphs, CPU dispatch overhead kills performance (14 tok/s). MTP compensates by predicting multiple tokens per forward pass, reducing round-trips. Use `--speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'`.
* **MTP is wrong for batched throughput.** Speculative decoding adds extra forward passes per step (accept/reject overhead). Under continuous batching with `--performance-mode throughput`, the GPU is already saturated across many concurrent requests — MTP wastes cycles generating tokens that could go to other requests. Drop the speculative config and use `--performance-mode throughput` for batch serving. Keep MTP + `--performance-mode interactivity` only for single-user, low-latency streams.
* **`--skip-mm-profiling` saves 2-3 GiB during startup** by skipping the multimodal encoder profiler. Useful when VRAM is tight. But vLLM may reallocate the saved memory to KV cache, so combine with lower `--gpu-memory-utilization` if the goal is to leave free headroom.
* **CUDA graphs vs MTP: MTP is the answer when CUDA graphs OOM.** CUDA graphs replay pre-recorded kernel sequences, eliminating per-step CPU→GPU launch overhead. But they require significant VRAM for capture. When the model is too large for CUDA graphs, use `--enforce-eager` + MTP instead of switching to a smaller model.
* **vLLM vs llama.cpp depends on VRAM headroom.** With 96GB, vLLM wins (continuous batching, PagedAttention, tool calling, speculative decoding). On a tight card (24 GiB), llama.cpp's minimal overhead gives more room for context.
* **Batch shape determines the right engine.** llama.cpp + GGUF often wins or competes for batch=1 interactive decode because overhead is low and quantized kernels are good. vLLM is the service/concurrency engine: continuous batching, KV management, OpenAI API ergonomics, tool/reasoning parsers, and aggregate throughput. RTX PRO 6000 shines more at high concurrency, huge contexts, FP8/BF16 formats, and multimodal serving than at making one stream 10x faster than a 3090.
* **Higher GPU utilization is not the goal by itself.** Dense models can make `nvidia-smi` look better while doing much more work per token and producing fewer tokens/sec. Optimize for direct API tokens/sec, latency, quality, and aggregate throughput.
* **Measure direct API before blaming the model/runtime.** Open WebUI or streaming UI measurements can understate backend throughput. Measured Qwen3.6-35B-A3B BF16 via direct non-streaming curl: 8,876 completion tokens in 98.81s (~89.8 tok/s) before adding `--optimization-level 3 --performance-mode interactivity`.
* MoE model names can be misleading — "4.7B" may refer to active params, not total. Check actual weight file sizes (`du -sh`) to estimate VRAM.
* GPU compute capability gates which features work. Blackwell (RTX PRO 6000): fp8 KV cache, FlashAttention, CUDA graphs all work. Ampere (RTX 3090): no fp8 KV cache with MLA, no FlashMLA.
* **Never use `--trust-remote-code` with community model repos.** It executes arbitrary Python from the HuggingFace repo. vLLM supports Qwen/major architectures natively without it.
* **vLLM KV cache is dynamic per-request (PagedAttention).** `--max-model-len` is the per-request cap, not a pre-allocation. A 131k max with 275k total KV cache tokens means 20+ concurrent 13k requests fit, or 2 concurrent 131k requests. Set max-model-len high; concurrency self-adjusts.

## Inference Engine Selection

* **Kernel maturity matters more than engine features.** vLLM with `--enforce-eager` (no CUDA graphs) on Qwen3.5-122B gave 14 tok/s instead of expected 200+. Two possible causes: (1) GDN hybrid attention layers using slow Triton/FLA kernels, or (2) CPU-bound kernel dispatch without CUDA graphs on a 2 GHz CPU. Both fit the data — don't assume one without evidence. When throughput is unexpectedly low, consider both kernel quality and CPU dispatch overhead.
* **Theoretical throughput estimate:** memory_bandwidth / (active_params_bytes). E.g. 1.8 TB/s / 5 GB (10B active params at 4-bit) ≈ 360 tok/s theoretical, ~50-70% of that in practice. If measured throughput is >10x below this, the bottleneck is not memory bandwidth — investigate kernel/compute issues.
* **Use `nvidia-smi dmon` to classify bottlenecks.** If memory utilization is near max, investigate weight/KV bandwidth and quantization. If SM and memory are both moderate (e.g. ~50% SM / ~35% mem), suspect kernel/runtime inefficiency, small MoE expert ops, sparse routing overhead, CUDA graph coverage, or measurement path rather than raw GPU limits.
* **SGLang** (`lmsysorg/sglang:latest`): OpenAI-compatible, similar to vLLM. Key flags: `--mem-fraction-static` (about gpu-memory-utilization), `--context-length` (about max-model-len), `--disable-cuda-graph` (about enforce-eager). No fixed entrypoint — use `python3 -m sglang.launch_server` as the command.
* **Bleeding-edge models can work with the right engine config.** Qwen3.5-122B (GDN hybrid) produced NaN on SGLang (DeepGemm format mismatch) and only 14 tok/s on vLLM without MTP. Fix was vLLM nightly + MTP + `--enforce-eager` + careful VRAM tuning. The issue was tooling config, not the model itself. Don't give up on a model until you've tried: different engines, speculative decoding, and memory tuning.
* **DeepGemm + AWQ on Blackwell = NaN.** SGLang's DeepGemm expects `ue8m0` scale format. AWQ 4-bit uses a different format → "accuracy degradation" warning → actual NaN output. Either disable DeepGemm or use a natively compatible quant format (FP8).
* **Format experiment order for Qwen3.6-35B-A3B:** first official FP8 in vLLM (quality-preserving, likely better VRAM/bandwidth), then GGUF Q4/Q5 in llama.cpp for fastest single-user local chat, then AWQ in vLLM if OpenAI serving plus smaller 4-bit weights is desired. Avoid `--trust-remote-code` for community quant repos unless proven necessary.

## Bleeding-edge Model Support in vLLM

* When a new model architecture isn't supported by `vllm/vllm-openai:latest`, use `nightly` tag instead. Don't try to pip-install transformers from git over the bundled version — vLLM pins internal dependencies and overriding them causes import errors (e.g. missing `layer_type_validation`).
* **Don't override bundled dependencies in specialized Docker images.** vLLM, torch, transformers are tightly coupled. Installing a different transformers version breaks vLLM's internal imports. If the stable image doesn't support your model, switch to nightly rather than patching packages.
* The `vllm/vllm-openai` image has entrypoint `["vllm", "serve"]`. Docker-compose `command:` should only provide the model path and flags — not repeat `vllm serve`. Otherwise you get `vllm vllm serve ...` → `unrecognized arguments: serve`.

## Model Management

* Models live in `/ssd/internet/huggingface.co/` on the host, mounted as `/huggingface.co/:ro` in inference containers. Mount the whole directory, not individual model paths — avoids deployment changes when swapping models.
* **Download workflow:** `hf download` on p-devbox to `~/devbox-ssd/` (writable), then `mv` on the host to `/ssd/internet/huggingface.co/`.
* **Switching the served model** touches the Podman Compose definition in `infra/0-box/configuration.nix` and any downstream consumers that hardcode model names: currently `ai/0-p-agent/opencode.json`, `ai/0-p-agent/agent-task.sh`, and `ai/0-p-agent/main.py` (bot command description). Check for other consumers with repo-wide `rg`.
